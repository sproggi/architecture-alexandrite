# Архитектурное решение по логированию

## 1. Мотивация

### 1.1. Почему логирование критически необходимо

Компания уже столкнулась с проблемами, которые невозможно решить без централизованного логирования:

- Заказы «зависают» на каком-то сервисе, и команда не может понять, где именно.
- Сообщения теряются при передаче между MES и CRM через RabbitMQ.
- Клиенты и пользователи API жалуются на неполученные заказы.
- Операторы MES видят непонятные статусы заказов.
- Потеряны крупные контракты из-за проблем с заказами.

**Корневая проблема:** логи разбросаны по разным системам (Shop API, CRM API, MES API, RabbitMQ, БД, фронтенды), нет единого места для их просмотра и анализа. Команда тратит часы на поиск причины инцидента, а иногда не может найти её вовсе.

**Логирование — это инструмент, который позволит:**
- Видеть полную картину событий в системе.
- Находить причину инцидента за минуты, а не часы.
- Коррелировать события между сервисами (через Trace ID и Order ID).
- Строить алерты и искать аномалии.
- Доказывать бизнесу, что система работает корректно (или где именно ломается).

### 1.2. Что даст логирование компании

| Проблема сейчас | Что даст логирование |
|---|---|
| «Заказ завис, непонятно где» | Логи всех сервисов с Trace ID позволяют восстановить полную картину. |
| «Сообщения теряются в RabbitMQ» | Логи публикации/потребления сообщений показывают, где потерялось. |
| «Клиент жалуется, что заказ не пришёл» | Можно найти все события по Order ID и понять, где остановился заказ. |
| «Непонятно, кто виноват — MES или CRM» | Логи связаны через Trace ID, видно, где произошла ошибка. |
| «Долго диагностируем инциденты» | Время диагностики сокращается с часов до минут. |
| «Не можем доказать, что проблема не в нашем коде» | Логи показывают, где именно произошла ошибка. |

### 1.3. Метрики, на которые повлияет внедрение логирования

#### Технические метрики

1. **Mean Time to Detect (MTTD)** — среднее время обнаружения проблемы.
   - До: часы или дни (клиент пожаловался).
   - После: минуты (алерт + логи).

2. **Mean Time to Resolve (MTTR)** — среднее время решения проблемы.
   - До: часы или дни.
   - После: минуты или часы.

3. **Количество ошибок 5xx, найденных через логи.**
   - До: неизвестно.
   - После: точная цифра с контекстом.

4. **Количество потерянных сообщений в RabbitMQ.**
   - До: неизвестно.
   - После: точная цифра с Order ID.

5. **Время прохождения заказа по статусам.**
   - До: только общее время.
   - После: разбивка по каждому сервису и этапу.

#### Бизнес-метрики

1. **Количество просроченных заказов.**
   - До: растёт.
   - После: снижается, потому что проблемы находятся быстрее.

2. **Количество жалоб от клиентов.**
   - До: растёт.
   - После: снижается, потому что проблемы решаются до жалоб.

3. **Количество потерянных контрактов.**
   - До: несколько за месяц.
   - После: снижается до нуля.

4. **NPS (Net Promoter Score) клиентов.**
   - До: падает.
   - После: растёт.

5. **Выручка по каналам (B2C, API).**
   - До: под угрозой.
   - После: стабильный рост.

## 2. Какие логи нужно собирать

### 2.1. Общие принципы

Все логи должны быть **структурированными** (JSON) и содержать:
- `timestamp` — время события.
- `level` — уровень (INFO, WARN, ERROR).
- `service` — название сервиса.
- `trace_id` — ID трейса (для корреляции).
- `span_id` — ID спана.
- `order_id` — ID заказа (если применимо).
- `user_id` — ID пользователя (если применимо).
- `message` — текст сообщения.
- `context` — дополнительные поля (зависят от сервиса).

### 2.3. Другие уровни логирования

| Уровень | Когда используем | Примеры |
|---|---|---|
| **DEBUG** | Для детальной диагностики в dev-окружении. Не включаем в prod (слишком много данных). | Значения переменных, SQL-запросы, содержимое сообщений. |
| **INFO** | Все значимые бизнес-события и технические операции. Основной уровень для prod. | Создание заказа, смена статуса, публикация сообщения. |
| **WARN** | Потенциальные проблемы, которые не сломали систему, но требуют внимания. | Медленный запрос, retry сообщения, приближение к лимиту. |
| **ERROR** | Ошибки, которые привели к сбою операции. | Ошибка 5xx, потеря сообщения, ошибка БД. |
| **CRITICAL** | Критические ошибки, которые привели к падению сервиса. | OOM, нехватка диска, недоступность БД. |

**Правила:**
- В prod используем INFO, WARN, ERROR, CRITICAL.
- DEBUG — только в dev.
- TRACE — не используем (заменяем трейсингом).

## 3. Приоритизация: что настраивать в первую очередь

Команда не может единовременно реализовать логирование и трейсинг всех систем. Поэтому нужно расставить приоритеты.

### 3.1. Критерии приоритизации

1. **Влияние на бизнес:** потеря заказов, жалобы клиентов, потеря контрактов.
2. **Срочность:** проблемы уже сейчас.
3. **Сложность:** ресурсы команды ограничены.
4. **Зависимости:** что нужно для корреляции логов и трейсов.

### 3.2. Приоритет 1: Критические системы (1–2 месяца)

| Система | Почему в первую очередь |
|---|---|
| **RabbitMQ** | Прямая причина потери заказов. Логи публикации/потребления/DLQ покажут, где теряются сообщения. |
| **MES API** | Узкое место производства. Логи расчёта стоимости, смены статусов, работы с 3D-файлами. |
| **CRM API** | Обработка заказов продавцами. Логи смены статусов, подтверждения, закрытия. |
| **Shop API** | Точка входа для B2C-заказов. Логи создания заказа, загрузки файла, публикации в RabbitMQ. |

**Почему:** эти четыре системы — ядро процесса заказа. Без их логов невозможно понять, где заказ «завис» или «потерялся».

### 3.3. Приоритет 2: Важные системы (2–4 месяца)

| Система | Почему во вторую очередь |
|---|---|
| **API для внешних продавцов** | Новый канал продаж, потеря контрактов. Логи запросов, ошибок, создания заказов. |
| **Shop DB / MES DB** | Единственные инстансы БД. Логи медленных запросов, ошибок, deadlock. |
| **S3 storage** | Хранение 3D-файлов. Логи загрузки/скачивания, ошибок. |

### 3.4. Приоритет 3: Фронтенды и вспомогательные системы (4–6 месяцев)

| Система | Почему в третью очередь |
|---|---|
| **Онлайн-магазин (Vue)** | Фронтенд-логи для понимания поведения пользователя. |
| **CRM (Vue)** | Фронтенд-логи для понимания поведения продавца. |
| **MES (React)** | Фронтенд-логи для понимания поведения оператора, времени загрузки дашборда. |

## 4. Предлагаемое решение

### 4.1. Технологии

| Компонент | Технология | Почему |
|---|---|---|
| **Сбор логов** | Fluent Bit / Fluentd | Легковесный, поддерживает все источники, хорошо работает в Kubernetes и на EC2. |
| **Транспорт** | Kafka (опционально) | Буферизация логов при высоких нагрузках. |
| **Хранение и поиск** | Elasticsearch (или OpenSearch) | Стандарт для логов, мощный поиск, агрегации. |
| **Визуализация** | Kibana (или Grafana) | Единая точка для логов, метрик и трейсов. |
| **Корреляция** | Trace ID + Order ID | Связь логов с трейсами и метриками. |
| **Алертинг** | ElastAlert / Grafana Alerting | Алерты на основе логов. |
| **Аномалии** | Elasticsearch ML / Grafana ML | Поиск аномалий в логах. |
| **Доставка логов из приложений** | Logback (Java), Serilog (C#), Winston (JS) | Стандартные библиотеки для структурированного логирования. |

### 4.2. Компоненты, которые нужно внедрить или доработать

#### Новые компоненты

1. **Fluent Bit** — развернуть на каждом EC2-инстансе (или как DaemonSet в Kubernetes).
   - Собирает логи из stdout/stderr приложений.
   - Собирает логи из файлов (если есть).
   - Обогащает логи (добавляет `service`, `environment`, `instance_id`).
   - Отправляет логи в Elasticsearch (или Kafka → Elasticsearch).

2. **Elasticsearch** — развернуть в Yandex Cloud (Managed Elasticsearch или self-hosted).
   - Хранит логи.
   - Предоставляет поиск и агрегации.
   - Индексирует по сервисам и датам.

3. **Kibana** — развернуть рядом с Elasticsearch.
   - Визуализация логов.
   - Дашборды по сервисам.
   - Поиск по Trace ID / Order ID.

4. **Kafka** (опционально) — для буферизации логов.
   - Fluent Bit отправляет логи в Kafka.
   - Logstash / Kafka Connect читает из Kafka и отправляет в Elasticsearch.
   - Нужна при высоких нагрузках.

5. **Grafana Alerting** — для алертинга на основе логов.
   - Алерты на ERROR, CRITICAL.
   - Алерты на аномалии (всплеск ошибок, DDoS).

#### Доработки существующих компонентов

1. **Shop API:**
   - Настроить Logback для структурированного JSON-логирования.
   - Добавить Trace ID и Order ID в MDC (Mapped Diagnostic Context).
   - Логировать все события из списка INFO.

2. **CRM API:**
   - Аналогично Shop API.

3. **MES API:**
   - Настроить Serilog для структурированного JSON-логирования.
   - Добавить Trace ID и Order ID в LogContext.
   - Логировать все события из списка INFO.

4. **RabbitMQ:**
   - Включить плагин `rabbitmq_tracing` (или использовать логи самого RabbitMQ).
   - Настроить логирование публикации/потребления/DLQ.

5. **Shop DB / MES DB:**
   - Включить `log_min_duration_statement = 1000` (логировать запросы > 1s).
   - Включить `log_connections`, `log_disconnections`.
   - Включить `log_lock_waits`, `log_deadlocks`.

6. **S3 storage:**
   - Включить логирование доступа (access logs).
   - Настроить логирование операций (upload, download, delete).

7. **Онлайн-магазин:**
   - Подключить Winston или Pino для структурированного логирования.
   - Отправлять логи на бэкенд (или в Fluent Bit через sidecar).

8. **CRM:**
   - Аналогично онлайн-магазину.

9. **MES:**
   - Аналогично онлайн-магазину.

10. **API для внешних продавцов:**
    - Настроить логирование запросов, ошибок, создания заказов.
    - Добавить Seller ID в логи.

### 4.4. Политика безопасности

#### 4.4.1. Чувствительные данные

**Что считаем чувствительным:**
- Персональные данные клиентов (ФИО, телефон, email, адрес).
- Данные об оплате (номера карт, транзакции).
- Данные о заказах (состав, стоимость).
- Данные о пользователях (логины, ID).
- Внутренние идентификаторы (Order ID, Trace ID) — не чувствительны, но могут быть использованы для атаки.

**Как работаем с чувствительными данными:**
1. **Маскирование:** в логи не попадают полные номера карт, телефоны, email. Вместо них — хеши или маски (например, `+7***1234`, `user_***@example.com`).
2. **Хеширование:** `user_id` хешируется (SHA-256) перед записью в лог.
3. **Исключение:** поля с чувствительными данными исключаются из логов на уровне приложения (через фильтры Logback/Serilog).
4. **Аудит:** все логи, содержащие чувствительные данные, помечаются тегом `sensitive=true` и требуют дополнительных прав доступа.

#### 4.4.2. Доступ к логам

**Кто имеет доступ:**
- **Разработчики** — доступ к логам своих сервисов (Shop API, CRM API, MES API).
- **QA** — доступ к логам в dev и release.
- **DevOps** — полный доступ ко всем логам.
- **Поддержка** — доступ к логам для диагностики инцидентов.
- **Продакт** — доступ к бизнес-логам (без технических деталей).
- **Администраторы** — полный доступ.

**Как реализуется:**
1. **Аутентификация:** SSO (Yandex ID, Keycloak). Только сотрудники компании.
2. **Авторизация:** RBAC. Роли: `developer`, `qa`, `devops`, `support`, `product`, `admin`.
3. **Аудит:** все доступы к Kibana логируются. Кто, когда, какой запрос выполнял.
4. **Шифрование:** TLS для передачи логов, шифрование at rest в Elasticsearch.
5. **Изоляция:** Kibana в приватной сети, доступ через VPN или bastion host.

#### 4.4.3. Защита от утечек

1. **DLP (Data Loss Prevention):** сканирование логов на наличие чувствительных данных.
2. **Rate limiting:** ограничение на количество запросов к Kibana.
3. **Экспорт:** запрет на экспорт больших объёмов логов без approval.
4. **Retention:** автоматическое удаление старых логов.

### 4.5. Политика хранения

#### 4.5.1. Индексы

**Отдельный индекс под каждую систему:**
- `logs-shop-api-YYYY.MM.DD`
- `logs-crm-api-YYYY.MM.DD`
- `logs-mes-api-YYYY.MM.DD`
- `logs-rabbitmq-YYYY.MM.DD`
- `logs-shop-db-YYYY.MM.DD`
- `logs-mes-db-YYYY.MM.DD`
- `logs-s3-YYYY.MM.DD`
- `logs-frontend-YYYY.MM.DD`
- `logs-api-external-YYYY.MM.DD`

**Почему отдельные индексы:**
- Проще управлять retention.
- Проще настраивать права доступа.
- Проще масштабировать.
- Меньше риск, что один сервис «зальёт» всё.

#### 4.5.2. Сроки хранения

| Тип логов | Срок хранения | Почему |
|---|---|---|
| **ERROR / CRITICAL** | 90 дней | Нужны для расследования инцидентов, postmortem. |
| **WARN** | 30 дней | Нужны для анализа трендов. |
| **INFO** | 14 дней | Нужны для оперативной диагностики. |
| **DEBUG** | 3 дня (только dev) | Быстро растут, не нужны в prod. |
| **Аудит-логи** | 1 год | Требование безопасности. |

**Как реализуется:**
- Index Lifecycle Management (ILM) в Elasticsearch.
- Автоматическое удаление старых индексов.
- Архивирование в S3 (для аудит-логов).

#### 4.5.3. Размер

**Оценка объёма:**
- Shop API: ~1 GB/день (при 1000 заказов/день).
- CRM API: ~500 MB/день.
- MES API: ~2 GB/день (расчёт стоимости, работа с 3D).
- RabbitMQ: ~500 MB/день.
- БД: ~200 MB/день.
- S3: ~100 MB/день.
- Фронтенды: ~300 MB/день.
- API external: ~500 MB/день.

**Итого:** ~5 GB/день, ~150 GB/месяц, ~450 GB за 90 дней.

**С учётом репликации (2 копии):** ~900 GB.

**Резерв:** 1.5 TB.

### 4.6. Превращение системы сбора логов в систему анализа логов

#### 4.6.1. Алертинг

**Что алертим:**
1. **ERROR / CRITICAL в логах:**
   - Любая запись уровня ERROR или CRITICAL → алерт.
   - Группировка по сервису и типу ошибки.
   - Если ошибок > 10 за 5 минут → critical.

2. **Аномалии:**
   - Всплеск ошибок 5xx → возможная DDoS-атака.
   - Всплеск создания заказов (10 000 за секунду) → возможная атака конкурентов.
   - Всплеск неудачных аутентификаций → брутфорс.

3. **Бизнес-события:**
   - Заказ в статусе > 3 недель → алерт продакту.
   - Заказ не двигается > 30 минут → алерт дежурному.
   - DLQ > 0 → critical.

4. **Технические события:**
   - Медленный запрос > 10s → warning.
   - Deadlock в БД → warning.
   - Разрыв соединения с БД → critical.

**Как реализуется:**
- **ElastAlert** — для алертов на основе логов в Elasticsearch.
- **Grafana Alerting** — для алертов на основе метрик (включая метрики из логов).
- **Alertmanager** — для маршрутизации алертов.
- **Каналы:** мессенджер, email, звонок дежурному (Twilio).

#### 4.6.2. Поиск аномалий

**Что ищем:**
1. **Всплеск создания заказов:**
   - Было 4 записи о создании заказов → стало 10 000 за секунду.
   - Возможная DDoS-атака конкурентами.
   - Действие: автоматически включить rate limiting, уведомить дежурного.

2. **Всплеск ошибок 5xx:**
   - Было 1% ошибок → стало 50%.
   - Возможная атака или баг после релиза.
   - Действие: автоматический откат, уведомление.

3. **Всплеск неудачных аутентификаций:**
   - Было 10/минуту → стало 10 000/минуту.
   - Брутфорс.
   - Действие: блокировка IP, уведомление.

4. **Аномальное поведение пользователя:**
   - Один пользователь генерирует 10 000 запросов/минуту.
   - Возможный бот.
   - Действие: блокировка, уведомление.

**Как реализуется:**
- **Elasticsearch ML** — встроенные модели для поиска аномалий.
- **Grafana ML** — если используем Grafana.
- **Кастомные правила** — через ElastAlert.
- **Интеграция с Alerting** — при обнаружении аномалии → алерт.

#### 4.6.3. Дашборды

**Какие дашборды нужны:**
1. **Общий дашборд** — количество логов по сервисам, уровень, ошибки.
2. **Дашборд заказов** — воронка заказов, статусы, время прохождения.
3. **Дашборд ошибок** — топ ошибок, тренды, корреляция с релизами.
4. **Дашборд безопасности** — неудачные аутентификации, аномалии, DDoS.
5. **Дашборд производительности** — медленные запросы, время ответа API.
6. **Дашборд бизнес-метрик** — заказы, выручка, конверсия.

**Как реализуется:**
- **Kibana** — для логов.
- **Grafana** — для метрик и трейсов.
- **Единая точка входа** — ссылки из Kibana в Grafana и Jaeger.
