## Планирование: анализ, идентификация проблем и поиск решений

## 1. Идентификация проблемных мест

### 1.1. Проблемы, напрямую влияющие на бизнес

1. **Рост нагрузки и деградация сроков выполнения заказов.**
   - Нагрузка растёт линейно: +100 заказов в месяц.
   - Клиенты жалуются на просрочки (обещали 3 недели, ждут месяцами).
   - Производственные мощности позволяют двукратный рост, значит проблема не в производстве, а в обработке заказов, коммуникации и пропускной способности системы.

2. **Проблемы с API для внешних продавцов.**
   - После открытия API компанию «завалило заказами».
   - Жалобы от пользователей API на неполученные заказы.
   - Заказ создаётся в CRM через получение сообщения из очереди от MES — это асинхронный сценарий, который, вероятно, теряет заказы или создаёт дубли/задержки.

3. **Потеря крупных контрактов из-за проблем с заказами.**
   - Через месяц после открытия API потеряно несколько крупных контрактов.
   - Недовольство B2C-клиентов растёт.

4. **Проблемы с производительностью MES (дашборд операторов).**
   - Первая страница MES долго прогружается.
   - Фильтр по статусам и пагинация не помогли.
   - Операторам важно видеть самые новые заказы (от этого зависит их вознаграждение).
   - Вероятная причина: неоптимальные запросы к БД, отсутствие индексов, загрузка всех данных на клиент, отсутствие кэширования, либо блокировки на чтение/запись в единственном инстансе БД.

5. **Единственный инстанс каждого приложения и БД.**
   - Нет горизонтального масштабирования.
   - Единая точка отказа.
   - При росте нагрузки (линейном) ресурсы исчерпываются.
   - БД работает на запись и чтение в одном инстансе — конкуренция за ресурсы, блокировки, деградация производительности.

6. **Ручной деплой в release и prod.**
   - Задержки релизов.
   - Человеческий фактор.
   - При росте команды и нагрузки это становится узким местом.

7. **Ручное E2E-тестирование и блокировка релизов при high/highest багах.**
   - Задержки релизов растут.
   - QA-инженер один, хочет автоматизацию, но прототипы не внедрены.
   - Чем больше функциональности, тем дольше регресс.

8. **Интеграция MES ↔ CRM через RabbitMQ, реализованная командой.**
   - Нет информации о гарантиях доставки, идемпотентности, retry, dead letter queue.
   - При росте заказов очередь может переполняться, сообщения теряться или обрабатываться с задержкой.
   - Заказ создаётся в CRM через сообщение от MES — если сообщение потеряно, заказ не создан, клиент не получил изделие.

9. **Отсутствие мониторинга и наблюдаемости.**
   - Не упоминается мониторинг, логирование, трейсинг, алертинг.
   - Без этого невозможно быстро диагностировать проблемы с заказами, очередями, БД.

10. **Расчёт стоимости в MES занимает 2–3 минуты, до 30 минут для сложных моделей.**
    - Это синхронная операция? Если да, то это блокирует пользователя и создаёт нагрузку.
    - Если асинхронная, то как уведомляется пользователь?
    - При росте заказов это становится бутылочным горлышком.

11. **Дисбаланс компетенций в команде.**
    - MES на C#, но в команде только один C#-разработчик (и тимлид — бывший C#).
    - Фронтенд: 2 Vue, 1 частично React, но MES на React.
    - Нет автоматизаторов тестирования.
    - Один DevOps.

12. **Отсутствие версионирования API и контрактов.**
    - Внешние продавцы используют API — при изменениях возможны поломки.
    - Нет упоминания о версионировании, документации, SLA.

## 2. Инициативы по устранению проблем

### 2.1. Инфраструктура и масштабирование

**И-1. Горизонтальное масштабирование приложений и БД.**
- Перевести приложения на несколько инстансов за балансировщиком.
- Разделить БД на read-replica для чтения и master для записи.
- Настроить автоскейлинг в Yandex Cloud.
- **Приоритет: высокий.** Без этого любой рост нагрузки приведёт к отказам.

**И-2. Внедрение мониторинга, логирования и алертинга.**
- Prometheus + Grafana, ELK/Loki, трассировка (OpenTelemetry).
- Алерты на: длину очередей RabbitMQ, время ответа API, ошибки 5xx, задержки БД, количество заказов в статусах.
- **Приоритет: высокий.** Без наблюдаемости нельзя управлять.

**И-3. Автоматизация CI/CD для release и prod.**
- Внедрить автоматический деплой после прохождения тестов.
- Использовать стратегии blue-green или canary.
- **Приоритет: средний.** Влияет на скорость релизов, но не критично для текущих проблем с заказами.

### 2.2. Интеграция и обработка заказов

**И-4. Аудит и доработка интеграции MES ↔ CRM через RabbitMQ.**
- Гарантии доставки: persistent messages, publisher confirms, consumer acks.
- Идемпотентность обработки сообщений.
- Retry с экспоненциальной задержкой, dead letter queue.
- Мониторинг очередей.
- **Приоритет: критический.** Потеря заказов — прямая причина жалоб.

**И-5. Аудит и доработка API для внешних продавцов.**
- Версионирование API.
- Rate limiting.
- Асинхронная обработка заказов с уведомлением о статусе.
- SLA и документация.
- **Приоритет: критический.** Потеря контрактов из-за API.

**И-6. Оптимизация расчёта стоимости в MES.**
- Вынести расчёт в асинхронную очередь.
- Кэширование результатов для типовых моделей.
- Оптимизация алгоритма расчёта (если возможно).
- **Приоритет: высокий.** 30 минут на расчёт — это неприемлемо.

**И-7. Оптимизация дашборда операторов в MES.**
- Индексы в БД.
- Пагинация на стороне сервера.
- Кэширование.
- WebSocket/SSE для обновления в реальном времени.
- **Приоритет: высокий.** Операторы — узкое место производства.

### 2.3. Тестирование и качество

**И-8. Внедрение автоматизированного тестирования.**
- E2E-тесты (Playwright/Cypress).
- Интеграционные тесты для API и очередей.
- Нагрузочное тестирование.
- **Приоритет: высокий.** Без этого релизы будут тормозить.

**И-9. Настройка тестовых данных и окружений.**
- Генерация тестовых 3D-моделей.
- Изолированные окружения для тестов.
- **Приоритет: средний.**

### 2.4. Команда и процессы

**И-10. Наём C#-разработчика и React-разработчика.**
- MES на C# и React — критический компонент.
- **Приоритет: высокий.**

**И-11. Наём QA-автоматизатора.**
- Внедрение автоматизации.
- **Приоритет: средний.**

**И-12. Внедрение практик SRE/DevOps.**
- Runbook, postmortem, on-call.
- **Приоритет: средний.**

### 2.5. Архитектура

**И-13. Выделение сервиса заказов (Order Service).**
- Единая точка управления жизненным циклом заказа.
- Оркестрация статусов.
- **Приоритет: средний.** Долгосрочная инициатива.

**И-14. Внедрение Event Sourcing / CQRS для заказов.**
- Аудит, восстановление, масштабирование чтения.
- **Приоритет: низкий.** Сложно, долго, не решает текущие проблемы.

**И-15. Кэширование (Redis) для часто читаемых данных.**
- Дашборд, статусы, каталог.
- **Приоритет: средний.**

## 3. Приоритизация инициатив

### 3.1. Критерии приоритизации

1. **Влияние на бизнес:** потеря контрактов, жалобы клиентов, просрочки.
2. **Срочность:** проблемы уже сейчас, а не в будущем.
3. **Сложность/стоимость:** ресурсы команды ограничены.
4. **Зависимости:** что нужно сделать раньше, чтобы работало потом.

### 3.2. Порядок приоритета

**Приоритет 1 (критический, делать немедленно):**
1. **И-4. Аудит и доработка интеграции MES ↔ CRM через RabbitMQ.**
2. **И-5. Аудит и доработка API для внешних продавцов.**
3. **И-2. Внедрение мониторинга, логирования и алертинга.**

**Приоритет 2 (высокий, в течение 1–2 месяцев):**
4. **И-1. Горизонтальное масштабирование приложений и БД.**
5. **И-7. Оптимизация дашборда операторов в MES.**
6. **И-6. Оптимизация расчёта стоимости в MES.**
7. **И-8. Внедрение автоматизированного тестирования.**
8. **И-10. Наём C#-разработчика и React-разработчика.**

**Приоритет 3 (средний, в течение 3–6 месяцев):**
9. **И-3. Автоматизация CI/CD для release и prod.**
10. **И-15. Кэширование (Redis).**
11. **И-9. Настройка тестовых данных и окружений.**
12. **И-11. Наём QA-автоматизатора.**
13. **И-12. Внедрение практик SRE/DevOps.**
14. **И-13. Выделение сервиса заказов.**

**Приоритет 4 (низкий, долгосрочно):**
15. **И-14. Event Sourcing / CQRS.**

### 3.3. Ход рассуждений

- **Сначала — остановить финансовые потери.** Потеря заказов и контрактов — это прямые финансовые потери. Поэтому И-4 и И-5 — первые.
- **Без мониторинга не видно проблем.** И-2 — третий, потому что без него мы не поймём, помогли ли И-4 и И-5, и не увидим новые проблемы.
- **Масштабирование — следующий шаг.** Когда заказы не теряются, нужно обеспечить пропускную способность. И-1.
- **Дашборд и расчёт — узкие места производства.** И-7 и И-6.
- **Тесты и люди — для устойчивости.** И-8 и И-10.
- **Остальное — по мере возможности.**

## 4. Целевая архитектура через полгода

### 4.1. Инфраструктура

- **Приложения:** каждое приложение (онлайн-магазин, CRM, MES) запущено в нескольких инстансах за балансировщиком. Автоскейлинг по CPU/памяти/длине очереди.
- **БД:** master для записи + несколько read-replica для чтения. Разделение чтения и записи на уровне приложений (CQRS).
- **Кэш:** Redis для сессий, часто читаемых данных, результатов расчёта.
- **Очереди:** RabbitMQ в кластере, с persistent messages, DLQ, мониторингом.
- **Мониторинг:** Prometheus + Grafana + Elasticsearch + Jaeger/OpenTelemetry.
- **CI/CD:** автоматический деплой в dev, release и prod после прохождения тестов. Blue-green/canary.

### 4.2. Приложения

- **Онлайн-магазин:** асинхронная обработка заказов, уведомления о статусе.
- **CRM:** интеграция с MES через надёжную очередь, идемпотентность, retry.
- **MES:** оптимизированный дашборд (серверная пагинация, индексы, кэш), асинхронный расчёт стоимости, WebSocket для обновлений.
- **API для внешних продавцов:** версионирование, rate limiting, документация, SLA, асинхронные уведомления.

### 4.3. Данные и статусы

- **Единый Order Service** (или выделенный модуль) для управления жизненным циклом заказа.
- **Event Sourcing** для аудита и восстановления (опционально).
- **Статусы** синхронизированы между системами через события.

### 4.4. Команда

- 2 C#-разработчика (MES).
- 2 React-разработчика (MES).
- 2 Vue-разработчика (онлайн-магазин, CRM).
- 3 Java-разработчика (онлайн-магазин, CRM).
- 2 QA-автоматизатора.
- 2 DevOps/SRE.
- Тимлид, продакт.

### 4.5. Процессы

- Двухнедельные спринты.
- Автоматические E2E-тесты в CI.
- Нагрузочное тестирование перед релизом.
- Постмортемы без поиска виновных.
- On-call rotation.

## 5. Три пункта на ближайшие полгода

### 1. И-4. Аудит и доработка интеграции MES ↔ CRM через RabbitMQ.

**Почему:**
- Это прямая причина потери заказов.
- Без этого все остальные улучшения не имеют смысла: заказы будут теряться.
- Относительно быстро можно внедрить: persistent messages, acks, retry, DLQ, идемпотентность.
- Эффект: немедленное сокращение жалоб на неполученные заказы.

### 2. И-5. Аудит и доработка API для внешних продавцов.

**Почему:**
- Потеря крупных контрактов — это стратегическая угроза.
- API — новый канал продаж, который должен работать надёжно.
- Нужны: версионирование, rate limiting, асинхронная обработка, уведомления, SLA.
- Эффект: сохранение текущих контрактов и возможность роста.

### 3. И-2. Внедрение мониторинга, логирования и алертинга.

**Почему:**
- Без наблюдаемости мы не знаем, что происходит.
- Мониторинг позволит быстро диагностировать проблемы с заказами, очередями, БД.
- Алерты позволят реагировать до того, как клиенты пожалуются.
- Эффект: снижение времени реакции на инциденты, предотвращение потерь.

**Почему не масштабирование?**
- Масштабирование важно, но если заказы теряются, масштабирование не поможет.
- Сначала нужно обеспечить надёжность, потом — производительность.

**Почему не тесты?**
- Тесты важны, но они не решают текущие проблемы с заказами.
- Их можно внедрять параллельно, но они не входят в топ-3.

**Почему не наём?**
- Наём — это ресурс, а не решение. Сначала нужно понять, какие именно люди нужны, и подготовить процессы.

## 7. Выводы

1. **Корневая проблема:** система не готова к линейному росту нагрузки. Единственные инстансы, ручной деплой, отсутствие мониторинга, ненадёжная интеграция — всё это приводит к потерям заказов и клиентов.

2. **Первые шаги:** обеспечить надёжность обработки заказов (RabbitMQ, API), внедрить мониторинг. Это остановит потери и даст данные для дальнейших решений.

3. **Следующие шаги:** масштабирование, оптимизация MES, автоматизация тестов и деплоя.

4. **Долгосрочно:** выделение сервиса заказов, Event Sourcing, SRE-практики.

5. **Команда:** нужно усилить C#/React-разработчиками, QA-автоматизатором, DevOps. Но наём должен быть обоснован и следовать за архитектурными решениями.

6. **Целевая архитектура через полгода:** масштабируемая, наблюдаемая, с автоматизированными тестами и деплоем, надёжной интеграцией и готовностью к дальнейшему росту.
