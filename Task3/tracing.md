# Архитектурное решение по трейсингу

## 1. Мотивация

### 1.1. Почему трейсинг критически необходим

Компания уже столкнулась с проблемами, которые невозможно решить без сквозного трейсинга:

- Заказы «зависают» на каком-то сервисе внутри IT-ландшафта, и команда не может понять, где именно.
- Сообщения теряются при передаче между MES и CRM через RabbitMQ.
- Клиенты и пользователи API жалуются на неполученные заказы, а команда не может найти причину.
- Операторы MES видят непонятные статусы заказов.
- Потеряны крупные контракты из-за проблем с заказами.

**Корневая проблема:** заказ проходит через множество компонентов (онлайн-магазин, Shop API, Shop DB, RabbitMQ, CRM, CRM API, MES, MES API, MES DB, S3), и на каждом этапе он может «сломаться» или «зависнуть». Без трейсинга команда видит только разрозненные логи в разных системах и не может восстановить полную картину.

**Трейсинг — это инструмент, который позволит:**
- Видеть полный путь заказа от создания до закрытия.
- Находить точку, где заказ «завис» или потерялся.
- Диагностировать проблемы за минуты, а не часы.
- Доказывать бизнесу, что система работает корректно (или где именно ломается).

### 1.2. Что даст трейсинг компании

| Проблема сейчас | Что даст трейсинг |
|---|---|
| «Заказ завис, непонятно где» | Полный путь заказа с временными метками на каждом этапе. |
| «Сообщения теряются в RabbitMQ» | Видно, было ли сообщение опубликовано, доставлено, обработано. |
| «Клиент жалуется, что заказ не пришёл» | Можно восстановить всю историю заказа и найти, где он остановился. |
| «Непонятно, кто виноват — MES или CRM» | Trace ID связывает все сервисы, видно, где произошла ошибка. |
| «Долго диагностируем инциденты» | Время диагностики сокращается с часов до минут. |
| «Не можем доказать, что проблема не в нашем коде» | Трейсинг показывает, где именно произошла ошибка. |

### 1.3. Метрики, на которые повлияет внедрение трейсинга

#### Технические метрики

1. **Mean Time to Detect (MTTD)** — среднее время обнаружения проблемы.
   - До трейсинга: часы или дни (клиент пожаловался).
   - После: минуты (алерт + trace).

2. **Mean Time to Resolve (MTTR)** — среднее время решения проблемы.
   - До: часы или дни.
   - После: минуты или часы.

3. **Количество заказов, потерянных на каждом переходе статуса.**
   - До: неизвестно.
   - После: точная цифра по каждому переходу.

4. **Количество сообщений в DLQ RabbitMQ.**
   - До: неизвестно.
   - После: точная цифра, с trace ID для каждого сообщения.

5. **Время прохождения заказа по статусам.**
   - До: только общее время.
   - После: разбивка по каждому сервису и этапу.

#### Бизнес-метрики

1. **Количество просроченных заказов.**
   - До: растёт.
   - После: снижается, потому что проблемы находятся быстрее.

2. **Количество жалоб от клиентов.**
   - До: растёт.
   - После: снижается, потому что проблемы решаются до жалоб.

3. **Количество потерянных контрактов.**
   - До: несколько за месяц.
   - После: снижается до нуля.

4. **NPS (Net Promoter Score) клиентов.**
   - До: падает.
   - После: растёт.

5. **Выручка по каналам (B2C, API).**
   - До: под угрозой.
   - После: стабильный рост.

## 2. Предлагаемое решение

### 2.1. Технологии

| Компонент | Технология | Почему |
|---|---|---|
| **Сбор трейсов** | OpenTelemetry SDK | Стандарт де-факто, поддержка всех языков (Java, C#, JS/TS). |
| **Коллектор** | OpenTelemetry Collector | Централизованный сбор, обработка, экспорт трейсов. |
| **Хранение трейсов** | Jaeger (или Tempo) | Open-source, хорошо интегрируется с Grafana. |
| **Визуализация** | Grafana | Единая точка для метрик, логов и трейсов. |
| **Корреляция** | Trace ID + Order ID | Связь между трейсами, метриками и логами. |
| **Пропагация контекста** | W3C Trace Context | Стандарт передачи Trace ID между сервисами. |
| **Логирование** | Loki (или Elasticsearch) | Связь логов с трейсами через Trace ID. |
| **Алертинг** | Alertmanager + Grafana | Алерты на основе трейсов и метрик. |

### 2.2. Компоненты, которые нужно внедрить или доработать

#### Новые компоненты

1. **OpenTelemetry Collector** — развернуть в Yandex Cloud (EC2 или Kubernetes).
   - Принимает трейсы от всех сервисов.
   - Обрабатывает (sampling, фильтрация, обогащение).
   - Экспортирует в Jaeger.

2. **Jaeger** — развернуть в Yandex Cloud (EC2 или Kubernetes).
   - Хранит трейсы.
   - Предоставляет UI для поиска и анализа.
   - Интегрируется с Grafana.

3. **Grafana** — уже может быть развёрнута для метрик, добавить datasource Jaeger.
   - Дашборды с трейсами.
   - Корреляция метрик и трейсов.

4. **Alerting** — Alertmanager + Grafana.
   - Алерты на основе трейсов (например, заказ в статусе > 30 минут).

#### Доработки существующих компонентов

1. **Shop API:**
   - Подключить OpenTelemetry Java Agent или Micrometer Tracing.
   - Добавить кастомные спаны для ключевых операций (создание заказа, загрузка файла).
   - Пропагировать Trace ID в RabbitMQ (через headers).

2. **CRM API:**
   - Подключить OpenTelemetry Java Agent.
   - Добавить кастомные спаны (обработка заказа, смена статуса).
   - Извлекать Trace ID из RabbitMQ headers.

3. **MES API:**
   - Подключить OpenTelemetry .NET SDK.
   - Добавить кастомные спаны (расчёт стоимости, работа с 3D-файлом).
   - Пропагировать Trace ID в RabbitMQ.

4. **RabbitMQ:**
   - Настроить пропагацию Trace ID через headers сообщений.
   - Настроить плагин для трейсинга (если есть).

5. **S3 storage:**
   - Добавить трейсинг операций через OpenTelemetry SDK (если возможно).

6. **Онлайн-магазин:**
   - Подключить OpenTelemetry JS SDK.
   - Трейсить действия пользователя (загрузка файла, оформление заказа).

7. **CRM:**
   - Подключить OpenTelemetry JS SDK.
   - Трейсить действия продавца.

8. **MES:**
   - Подключить OpenTelemetry JS SDK.
   - Трейсить действия оператора, время загрузки дашборда.

9. **API для внешних продавцов:**
   - Добавить поддержку W3C Trace Context.
   - Принимать Trace ID от внешних систем (если они его передают).
   - Генерировать Trace ID, если не передан.

## 3. Компромиссы

### 3.1. Когда трейсинг не принесёт пользы

1. **Проприетарные системы, которые не поддерживают OpenTelemetry.**
   - Если MES — купленный софт с закрытым исходным кодом, может не быть возможности добавить трейсинг.
   - Решение: использовать лог-трейсинг (анализ логов) или договориться с вендором.

2. **Старые версии языков/фреймворков.**
   - Если Java-версия старая, OpenTelemetry Agent может не работать.
   - Решение: обновить версию или использовать ручной трейсинг.

3. **Высокая нагрузка.**
   - Трейсинг добавляет overhead (CPU, память, сеть).
   - Решение: использовать sampling (например, 10% трейсов).

4. **Отсутствие культуры observability.**
   - Если команда не умеет пользоваться трейсами, они будут бесполезны.
   - Решение: обучение, runbook, регулярные review.

### 3.2. Когда трейсинг пока невозможен

1. **Нет доступа к коду.**
   - Если какой-то компонент - чёрный ящик, трейсинг невозможен.
   - Решение: трейсинг на уровне инфраструктуры (сеть, логи).

2. **Нет ресурсов на внедрение.**
   - Внедрение трейсинга требует времени и людей.
   - Решение: начать с критических компонентов (RabbitMQ, Shop API, CRM API, MES API).

3. **Нет инфраструктуры.**
   - Нужен кластер для Jaeger, OpenTelemetry Collector, Grafana.
   - Решение: использовать managed-сервисы (например, Yandex Cloud Tracing).

### 3.3. Когда трейсинг обойдётся слишком дорого

1. **Полный трейсинг всех запросов.**
   - Хранение всех трейсов может быть дорогим.
   - Решение: sampling, retention policy (хранить 7 дней).

2. **Трейсинг фронтенда.**
   - Добавляет нагрузку на браузер пользователя.
   - Решение: трейсить только ключевые действия.

3. **Трейсинг БД.**
   - Может замедлить запросы.
   - Решение: использовать postgres_exporter + логи медленных запросов.

### 3.4. Компромиссы по данным

1. **Выбор определенных трейсов.**
   - Не все трейсы сохраняются.
   - Решение: 100% для ошибок, 10% для успешных.

2. **Период хранения.**
   - Трейсы хранятся ограниченное время.
   - Решение: 7 дней для трейсов, 30 дней для агрегированных метрик.

3. **Детализация.**
   - Не все данные попадают в трейс.
   - Решение: фокус на ключевых бизнес-данных (order_id, status, error).

## 4. Безопасность

### 4.1. Внутренняя безопасность

1. **Аутентификация.**
   - Доступ к Jaeger, Grafana, OpenTelemetry Collector — только через SSO (Yandex ID, Keycloak).
   - Только сотрудники компании с актуальной учётной записью.
   - Роли: «Разработчик» (просмотр), «Поддержка» (просмотр + поиск), «Администратор» (управление).

2. **Авторизация.**
   - RBAC.
   - Разработчики видят только свои сервисы.
   - Поддержка видит все сервисы, но не может менять настройки.
   - Администраторы могут всё.

3. **Шифрование.**
   - TLS для передачи трейсов между сервисами и Collector.
   - Шифрование данных в Jaeger.
   - Шифрование данных в Grafana.

4. **Аудит.**
   - Логирование всех доступов к трейсам.
   - Кто, когда, какой Trace ID смотрел.
   - Хранение аудит-логов 1 год.

5. **Изоляция.**
   - OpenTelemetry Collector в приватной сети.
   - Jaeger в приватной сети.
   - Доступ только через VPN.

### 4.2. Внешняя безопасность

1. **API для внешних продавцов.**
   - Внешние системы могут передавать Trace ID.
   - Валидация Trace ID (формат W3C Trace Context).
   - Не принимать Trace ID от неаутентифицированных систем.

2. **Данные в трейсах.**
   - Не включать PII (персональные данные) в трейсы.
   - Маскировать чувствительные данные (номера карт, адреса).
   - Использовать хеширование для user_id.

3. **Rate limiting.**
   - Ограничение на количество трейсов от внешних систем.
   - Защита от flooding.

4. **DDoS-защита.**
   - Ограничение на размер трейсов.
   - Ограничение на количество спанов в одном трейсе.
   - Защита OpenTelemetry Collector от перегрузки.

### 5.3. Автоматический мониторинг процесса прохождения заказа на основе трейсинга

#### 5.3.1. Идея

Каждый заказ имеет уникальный `Order ID`, который совпадает с `Trace ID`. Все спаны, относящиеся к заказу, содержат атрибут `order_id`. Это позволяет:

1. **Автоматически определять текущий статус заказа** по последнему завершённому спану.
2. **Автоматически измерять время нахождения заказа в каждом статусе** как разницу между временными метками спанов.
3. **Автоматически обнаруживать «зависшие» заказы** — если заказ находится в одном статусе дольше порогового значения.
4. **Автоматически строить воронку прохождения заказов** — сколько заказов на каждом этапе, сколько теряется.

#### 5.3.2. Как это работает

**Шаг 1. Сбор трейсов.**
Все сервисы (Shop API, CRM API, MES API, фронтенды) отправляют спаны в OpenTelemetry Collector. Каждый спан содержит:
- `trace_id` = `order_id`
- `span_id`
- `name` (например, `createOrder`, `calculatePrice`, `manufacturingStarted`)
- `start_time`, `end_time`
- `status` (OK/ERROR)
- Атрибуты: `order_id`, `order_status`, `user_id`, `seller_id`, `operator_id`, `model_polygons_count` и т.д.

**Шаг 2. Обработка в OpenTelemetry Collector.**
- **spanmetrics processor** — автоматически генерирует метрики из спанов:
  - `traces_spanmetrics_latency` (гистограмма длительности)
  - `traces_spanmetrics_calls_total` (счётчик вызовов)
  - `traces_spanmetrics_errors_total` (счётчик ошибок)
  - Метрики агрегируются по `service_name`, `operation`, `status`, `order_status`.
  - Экспортируются в Prometheus.

- **order_tracking processor** (кастомный или через OTTL) — агрегирует спаны по `trace_id` (= `order_id`):
  - Определяет текущий статус заказа.
  - Вычисляет время нахождения в каждом статусе.
  - Генерирует метрики:
    - `order_status_duration_seconds{order_id, status}` — время в статусе.
    - `order_stuck_total{order_id, status, threshold}` — заказ завис.
    - `order_completed_total{order_id}` — заказ завершён.
    - `order_status_transitions_total{from_status, to_status}` — переходы.
  - Отправляет события в Kafka (если настроено).

- **tail_sampling processor** — сохраняет 100% трейсов с ошибками и «зависших» заказов, 10% успешных.

**Шаг 3. Хранение и визуализация.**
- **Prometheus** хранит метрики от spanmetrics и order_tracking.
- **Jaeger** хранит трейсы.
- **Grafana** визуализирует:
  - **Order Funnel Dashboard** — воронка заказов: сколько на каждом этапе, сколько потеряно.
  - **Order Timeline Dashboard** — временная шкала конкретного заказа.
  - **Stuck Orders Dashboard** — список «зависших» заказов с указанием статуса и времени.
  - **SLA Dashboard** — процент заказов, выполненных в срок.

**Шаг 4. Алертинг.**
Grafana Alerting / Alertmanager на основе метрик из Prometheus:
- **Критические алерты:**
  - `order_stuck_total{status="PRICE_CALCULATED"} > 0` — заказ завис на расчёте стоимости > 30 минут.
  - `order_stuck_total{status="MANUFACTURING_STARTED"} > 0` — заказ в производстве > 3 недель.
  - `order_stuck_total{status="PACKAGING"} > 0` — заказ на упаковке > 2 дней.
  - `order_status_duration_seconds{status="SUBMITTED"} > 3600` — заказ не обработан > 1 часа.
- **Предупреждающие алерты:**
  - `order_stuck_total{status="FILE_UPLOADED"} > 5` — 5+ заказов с загруженным файлом, но не оформленных.
  - `order_status_transitions_total{from_status="PRICE_CALCULATED", to_status="MANUFACTURING_APPROVED"} < expected` — падение конверсии.
- **Бизнес-алерты:**
  - `order_completed_total` падает — заказы не завершаются.
  - `order_status_duration_seconds{quantile="0.95"} > SLA` — 95% заказов превышают SLA.

**Шаг 5. Реакция на алерты.**
- **Warning:** тикет в Jira + уведомление в мессенджер.
- **Critical:** звонок дежурному + тикет + уведомление продакта.
- **Автоматические действия:**
  - При `order_stuck_total{status="PRICE_CALCULATED"} > 0` — автоматически перезапустить расчёт или уведомить оператора.
  - При `order_stuck_total{status="MANUFACTURING_STARTED"} > 0` — уведомить оператора и менеджера.
  - При падении `order_completed_total` — остановить приём новых заказов (circuit breaker).

#### 5.3.4. Пример: как обнаруживается «зависший» заказ

1. Заказ #12345 создан в 10:00.
2. Shop API создаёт спан `createOrder` (10:00:00).
3. CRM API создаёт спан `processOrder` (10:00:05).
4. MES API создаёт спан `calculatePrice` (10:00:10).
5. Расчёт стоимости занимает 45 минут (вместо 2–3 минут).
6. OpenTelemetry Collector генерирует метрику `order_status_duration_seconds{order_id="12345", status="PRICE_CALCULATED"} = 2700`.
7. Grafana Alerting срабатывает: `order_stuck_total{status="PRICE_CALCULATED"} > 0`.
8. Alertmanager отправляет:
   - Тикет в Jira: «Заказ #12345 завис на расчёте стоимости > 30 минут».
   - Уведомление в мессенджер дежурному.
   - Звонок дежурному (если critical).
9. Дежурный открывает Grafana, видит трейс заказа #12345, находит спан `calculatePrice` с длительностью 45 минут.
10. Причина: сложная 3D-модель (1M полигонов).
11. Решение: оптимизировать алгоритм, добавить приоритет, уведомить клиента.

### 5.4. Как это будет работать (сквозной сценарий)

1. **Пользователь создаёт заказ в онлайн-магазине.**
   - Фронтенд генерирует Trace ID (= Order ID) и передаёт его в Shop API.
   - Shop API создаёт спан `createOrder`, сохраняет заказ в Shop DB.
   - Shop API публикует сообщение в RabbitMQ с Trace ID в headers.
   - Shop API отправляет спан в OpenTelemetry Collector.

2. **CRM получает сообщение из RabbitMQ.**
   - CRM API извлекает Trace ID из headers.
   - Создаёт спан `processOrder`, обновляет статус в Shop DB.
   - Публикует сообщение в RabbitMQ для MES.
   - Отправляет спан в OpenTelemetry Collector.

3. **MES получает сообщение из RabbitMQ.**
   - MES API извлекает Trace ID.
   - Создаёт спан `calculatePrice`, скачивает 3D-файл из S3.
   - Создаёт спан `manufacturing`, обновляет статус в MES DB.
   - Публикует сообщение в RabbitMQ для CRM.
   - Отправляет спаны в OpenTelemetry Collector.

4. **OpenTelemetry Collector обрабатывает спаны.**
   - spanmetrics processor генерирует метрики: `traces_spanmetrics_latency`, `traces_spanmetrics_calls_total`, `traces_spanmetrics_errors_total`.
   - order_tracking processor агрегирует спаны по `order_id` и генерирует метрики: `order_status_duration_seconds`, `order_stuck_total`, `order_completed_total`.
   - Экспортирует метрики в Prometheus.
   - Экспортирует трейсы в Jaeger.
   - Экспортирует трейсы в Kafka для Order Tracking Service.

5. **Order Tracking Service обрабатывает события.**
   - Читает трейсы из Kafka.
   - Агрегирует по `order_id`.
   - Определяет текущий статус заказа.
   - Вычисляет время в статусе.
   - Генерирует метрики в Prometheus.
   - Отправляет события в Alerting при превышении порогов.

6. **Grafana визуализирует.**
   - Order Funnel Dashboard — воронка заказов.
   - Order Timeline Dashboard — временная шкала заказа.
   - Stuck Orders Dashboard — «зависшие» заказы.
   - SLA Dashboard — соблюдение сроков.

7. **Alerting срабатывает.**
   - При `order_stuck_total{status="PRICE_CALCULATED"} > 0` — тикет + уведомление + звонок.
   - При `order_status_duration_seconds{status="MANUFACTURING_STARTED"} > 3 недель` — эскалация.
   - При падении `order_completed_total` — остановка приёма заказов.

8. **Команда реагирует.**
   - Дежурный открывает Grafana, видит трейс, находит проблему.
   - Исправляет, заказ двигается дальше.
   - Postmortem, если нужно.
