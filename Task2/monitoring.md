# Выбор и настройка мониторинга в системе

## 1. Мотивация

### 1.1. Почему мониторинг критически необходим именно сейчас

Компания находится в точке активного роста: нагрузка растёт линейно (+100 заказов в месяц), открыт API для внешних продавцов, идут новые рынки сбыта. При этом уже сейчас наблюдаются серьёзные проблемы:

- Клиенты жалуются на просроченные заказы.
- Пользователи API ежедневно сообщают о неполученных заказах.
- Потеряно несколько крупных контрактов.
- Операторы MES страдают от долгой загрузки дашборда.
- Растёт недовольство B2C-клиентов.

Все эти проблемы объединяет одно: **у компании нет объективной картины того, что происходит в системе в реальном времени**. Единственный источник данных — Яндекс Метрика — покрывает только фронтенд онлайн-магазина B2C. Она не видит:

- API-заказы от внешних продавцов.
- Внутренние процессы CRM и MES.
- Очереди RabbitMQ.
- Состояние баз данных.
- Время расчёта стоимости в MES.
- Задержки между сменами статусов заказа.

### 1.2. Что даст мониторинг бизнесу

| Проблема сейчас | Что даст мониторинг |
|---|---|
| «Клиенты жалуются, что заказ не пришёл» | Видимость полного жизненного цикла заказа: где он застрял, сколько времени находится в каждом статусе, кто ответственный. |
| «Пользователи API не получают заказы» | Метрики по API: количество запросов, ошибки, задержки, успешность создания заказов. |
| «Дашборд MES долго грузится» | Метрики времени ответа, количества запросов, загрузки БД. |
| «Мы теряем контракты» | Раннее предупреждение: алерты до того, как клиент пожалуется. |
| «Не понимаем, где узкое место» | Трассировка и метрики по каждому компоненту: магазин, CRM, MES, RabbitMQ, БД. |
| «Релизы задерживаются» | Метрики CI/CD, времени прохождения тестов, частоты деплоев. |
| «Производство может выдержать двукратный рост, но что-то мешает» | Пропускная способность каждого компонента, очереди, задержки. |

### 1.3. Экономическое обоснование

- **Потеря одного крупного контракта** — это прямые финансовые потери, которые многократно превышают стоимость внедрения мониторинга.
- **Репутационные потери** от жалоб клиентов сложно оценить, но они напрямую влияют на LTV и приток новых клиентов.
- **Мониторинг позволяет перейти от реактивного режима** («клиент пожаловался — разбираемся») **к проактивному** («алерт сработал — починили до жалобы»).
- **Без мониторинга невозможно доказать**, что инициативы по улучшению (масштабирование, оптимизация) действительно помогают. Мониторинг — это инструмент измерения эффективности вложений в разработку.

## 2. Выбор подхода к мониторингу

Для разных частей системы будем использовать разные подходы.

### 2.1. RED (Rate, Errors, Duration) — для API и сервисов

**Где применять:**
- Shop API (Spring Boot)
- CRM API (Spring Boot)
- MES API (C#)
- API для внешних продавцов

**Почему:**
- RED — это подход для сервисов, обрабатывающих запросы. Он отвечает на вопросы: сколько запросов приходит, сколько из них с ошибками, сколько времени занимает обработка.
- Это именно то, что нужно для диагностики проблем с заказами через API и онлайн-магазин.

**Метрики:**
- **Rate** — количество запросов в секунду.
- **Errors** — количество ошибок (4xx, 5xx).
- **Duration** — время ответа (p50, p95, p99).

### 2.2. USE (Utilization, Saturation, Errors) — для инфраструктуры

**Где применять:**
- EC2-инстансы (CPU, память, диск, сеть)
- PostgreSQL (Shop DB, MES DB)
- RabbitMQ
- S3-based storage

**Почему:**
- USE — это подход для ресурсов. Он отвечает на вопросы: насколько ресурс загружен, есть ли очередь на его использование, были ли ошибки.
- Это критически важно, потому что у компании сейчас **единственный инстанс каждого приложения и БД**, и они могут стать узким местом.

**Метрики:**
- **Utilization** — процент использования ресурса (CPU, память, диск).
- **Saturation** — длина очереди, количество ожидающих запросов.
- **Errors** — количество ошибок на ресурсе.

### 2.3. «Четыре золотых сигнала» — для бизнес-процессов и сквозного мониторинга

**Где применять:**
- Жизненный цикл заказа (от INITIATED до CLOSED)
- Интеграция MES <> CRM через RabbitMQ
- Дашборд операторов MES
- Процесс производства

**Почему:**
- «Четыре золотых сигнала» (Latency, Traffic, Errors, Saturation) — это универсальный подход, который хорошо ложится на бизнес-процессы.
- Он позволяет видеть систему целиком: сколько заказов, как быстро они проходят, где ошибаются, где скапливаются.

**Метрики:**
- **Latency** — время прохождения заказа по статусам.
- **Traffic** — количество заказов в единицу времени.
- **Errors** — количество заказов, которые не дошли до CLOSED.
- **Saturation** — сколько заказов «зависло» в каждом статусе.

## 3. Метрики и их обоснование

### 3.1. Метрики для RabbitMQ (USE + «Четыре золотых сигнала»)

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Number of dead-letter-exchange letters in RabbitMQ** | Если сообщения попадают в DLX — заказы теряются. Это прямая причина жалоб клиентов и пользователей API. Алерт при любом значении > 0. | `queue_name`, `exchange`, `reason` (rejected, expired, maxlen) |
| **Number of message in flight in RabbitMQ** | Показывает, сколько сообщений сейчас обрабатывается. Если значение растёт — потребители не справляются, очередь будет расти. | `queue_name`, `consumer` |

### 3.2. Метрики для API (RED)

#### 3.2.1. Rate (нагрузка)

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Number of requests (RPS) for internet shop API** | Понимать общую нагрузку на магазин. Основа для прогноза роста (+100 заказов/мес). | `endpoint`, `method`, `status` |
| **Number of requests (RPS) for CRM API** | Понимать нагрузку на CRM. Если растёт — продавцы активно работают. | `endpoint`, `method`, `status` |
| **Number of requests (RPS) for MES API** | Понимать нагрузку на MES. Критично, т.к. MES — узкое место. | `endpoint`, `method`, `status` |
| **Number of requests (RPS) per user for internet shop API** | Видеть аномалии: один пользователь может генерировать слишком много запросов (боты, DDoS, баги). | `user_id`, `endpoint` |
| **Number of requests (RPS) per user for CRM API** | Понимать поведение продавцов. Если у одного резко выросло — возможно, проблема. | `user_id`, `endpoint` |
| **Number of requests (RPS) per user for MES API** | Понимать поведение операторов. Если у одного резко выросло — возможно, проблема с UI. | `user_id`, `endpoint` |

#### 3.2.2. Errors (ошибки)

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Number of HTTP 200 for shop API** | Базовый показатель успешных запросов. Позволяет считать error rate. | `endpoint`, `method` |
| **Number of HTTP 200 for CRM API** | Базовый показатель успешных запросов. | `endpoint`, `method` |
| **Number of HTTP 200 for MES API** | Базовый показатель успешных запросов. | `endpoint`, `method` |
| **Number of HTTP 500 for shop API** | Прямой индикатор проблем на бэкенде магазина. Если растёт — клиенты не могут оформить заказ. | `endpoint`, `method`, `error_type` |
| **Number of HTTP 500 for CRM API** | Прямой индикатор проблем в CRM. Если растёт — продавцы не могут обрабатывать заказы. | `endpoint`, `method`, `error_type` |
| **Number of HTTP 500 for MES API** | Прямой индикатор проблем в MES. Если растёт — операторы не могут работать, заказы стоят. | `endpoint`, `method`, `error_type` |


#### 3.2.3. Duration (время ответа)

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Response time (latency) for shop API** | Если магазин тормозит — падает конверсия. | `endpoint`, `method`, `quantile` (p50, p95, p99) |
| **Response time (latency) for CRM API** | Если CRM тормозит — продавцы медленно обрабатывают заказы. | `endpoint`, `method`, `quantile` |
| **Response time (latency) for MES API** | Если MES тормозит — операторы не видят заказы, производство стоит. | `endpoint`, `method`, `quantile` |

### 3.3. Метрики ресурсов приложений (USE)

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **CPU % for shop API** | Единственный инстанс — если CPU зашкаливает, магазин тормозит. | `instance_id`, `environment` |
| **CPU % for CRM API** | Единственный инстанс — если CPU зашкаливает, CRM тормозит. | `instance_id`, `environment` |
| **CPU % for MES API** | Единственный инстанс — MES критичен для производства. | `instance_id`, `environment` |
| **Memory Utilisation for shop API** | Нехватка памяти приводит к OOM и падениям. | `instance_id`, `environment` |
| **Memory Utilisation for CRM API** | Нехватка памяти приводит к OOM и падениям. | `instance_id`, `environment` |
| **Memory Utilisation for MES API** | Нехватка памяти приводит к OOM и падениям. MES особенно критичен. | `instance_id`, `environment` |

### 3.4. Метрики баз данных (USE)

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Memory Utilisation for shop db instance** | Единственный инстанс БД — нехватка памяти приводит к swap и деградации. | `db_name`, `instance_type` |
| **Memory Utilisation for MES db instance** | Единственный инстанс БД — критично для производства. | `db_name`, `instance_type` |
| **Number of connections for shop db instance** | Если соединений много — БД может исчерпать лимит, магазин упадёт. | `db_name`, `application` |
| **Number of connections for MES db instance** | Если соединений много — MES не сможет обрабатывать заказы. | `db_name`, `application` |
| **Size of shop db instance** | Прогнозировать рост и необходимость масштабирования. | `db_name`, `table` |
| **Size of MES db instance** | Прогнозировать рост и необходимость масштабирования. | `db_name`, `table` |

### 3.5. Метрики хранилища S3

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Size of S3 storage** | 3D-файлы растут — нужно прогнозировать затраты и лимиты. | `bucket`, `file_type` |

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Number of simultaneous sessions for shop API** | Понимать, сколько пользователей одновременно в магазине. Коррелирует с нагрузкой. | `environment`, `region` |
| **Number of simultaneous sessions for CRM API** | Понимать, сколько продавцов работают одновременно. | `environment`, `role` |
| **Number of simultaneous sessions for MES API** | Понимать, сколько операторов работают одновременно. | `environment`, `shift` |
| **Kb transferred (received) for shop API** | Понимать входящий трафик (загрузка 3D-файлов). | `endpoint`, `method` |

| **Kb provided (sent) for shop API** | Понимать исходящий трафик (отдача 3D-файлов, каталога). | `endpoint`, `method` |

| **Kb provided (sent) for MES API** | Понимать исходящий трафик (отдача списка заказов, 3D-моделей). | `endpoint`, `method` |

## 4. Пример сценария

**Проблема:** клиент жалуется, что заказ не пришёл.

**Без мониторинга:**
- Менеджер идёт в CRM, смотрит статус.
- Если статус непонятный — идёт в MES, смотрит там.
- Если и там непонятно — идёт к разработчикам.
- Разработчики смотрят логи, но их может не быть.
- Время диагностики: часы или дни.

**С мониторингом:**
- Алерт: «Number of dead-letter-exchange letters in RabbitMQ > 0».
- Дежурный открывает дашборд: видит, что сообщения попадают в DLX.
- Причина: MES API не может обработать сообщение из-за ошибки.
- Дополнительно смотрит: `Number of HTTP 500 for MES API` вырос, `Number of message in flight in RabbitMQ` растёт.
- Решение: починить баг в MES API, переобработать сообщения из DLX.
- Время диагностики: минуты.

## 5. Приоритизация внедрения мониторинга

| Приоритет | Что внедряем | Почему |
|---|---|---|
| **1** | `Number of dead-letter-exchange letters in RabbitMQ`, `Number of message in flight in RabbitMQ` | Прямая причина потери заказов. |
| **2** | `Number of HTTP 500 for shop/CRM/MES API`, `Number of HTTP 200 for shop/CRM/MES API` | Прямая причина потери контрактов и жалоб. |
| **3** | `Response time (latency) for shop/CRM/MES API` | Если API тормозит — клиенты уходят. |
| **4** | `Number of requests (RPS) for shop/CRM/MES API` и `per user` | Понимать нагрузку и аномалии. |

| **6** | `Memory Utilisation`, `Number of connections`, `Size` для shop/MES DB | Единственные инстансы БД — критический ресурс. |
| **7** | `Number of simultaneous sessions` для shop/CRM/MES API | Понимать реальную активность пользователей. |
| **8** | `Kb transferred (received)`, `Kb provided (sent)` для shop/CRM/MES API | Понимать сетевую нагрузку, особенно для 3D-файлов. |

## 8. План действий

### 8.1. Развернуть инфраструктуру мониторинга

1. **Создать инстанс time-series базы данных**
Prometheus в Yandex Cloud. 
2. **Развернуть Grafana** для визуализации метрик. Настроить дашборды по компонентам: RabbitMQ, Shop API, CRM API, MES API, БД, S3.
3. **Развернуть Alertmanager** для управления алертами. Настроить маршрутизацию: критические алерты — в оповещение в мессенджер + звонок дежурному, некритические — в тикет-систему.
4. **Развернуть экспортеры метрик:**
   - `node_exporter` на каждый EC2-инстанс (CPU, память, диск, сеть).
   - `postgres_exporter` для Shop DB и MES DB (соединения, slow queries, размер).
   - `rabbitmq_exporter` для RabbitMQ (DLX, in-flight, очереди).
   - `nginx_exporter` / `haproxy_exporter` при наличии балансировщика.
5. **Настроить сбор метрик с приложений:**
   - Shop API и CRM API (Spring Boot): подключить Micrometer + Prometheus-эндпоинт `/actuator/prometheus`.
   - MES API (C#): подключить `prometheus-net` и экспонировать `/metrics`.
6. **Настроить сбор логов** 
    Настроить Elasticsearch и трассировку (Jaeger/OpenTelemetry) для сквозной диагностики.

### 8.2. Внедрить метрики в приложения

1. **Добавить кастомные метрики в Shop API:**
   - RPS, HTTP 200/500, latency (p50/p95/p99) через Micrometer.
   - Количество заказов в час по статусам.
   - Ошибки при загрузке 3D-файлов.
2. **Добавить кастомные метрики в CRM API:**
   - RPS, HTTP 200/500, latency.
   - Количество заказов в статусе MANUFACTURING_APPROVED.
   - Время от PRICE_CALCULATED до MANUFACTURING_APPROVED.
   - Ошибки при работе с RabbitMQ.
3. **Добавить кастомные метрики в MES API:**
   - RPS, HTTP 200/500, latency.
   - Время расчёта стоимости (гистограмма).
   - Время загрузки дашборда операторов.
   - Количество заказов, «зависших» в каждом статусе.
   - Количество активных операторов.
4. **Настроить метрики RabbitMQ:**
   - DLX letters, in-flight messages, queue size, publish/consume rate.
   - Настроить DLQ и мониторинг попадания в неё.

### 8.3. Настроить алерты

1. **Критические алерты (звонок дежурному + мессенджер):**
   - DLX letters > 0.
   - HTTP 500 rate > 1% за 5 минут для любого API.
   - Latency p95 > 5 секунд для любого API.
   - CPU > 85% или Memory > 85% на любом инстансе > 5 минут.
   - Number of connections к БД > 80% от лимита.
2. **Предупреждающие алерты (мессенджер + тикет):**
   - In-flight messages растёт > 10 минут.
   - Queue size растёт > 10 минут.
   - CPU > 70% или Memory > 70% > 10 минут.
   - Size of DB > 80% от выделенного.
   - Size of S3 > 80% от лимита.
3. **Бизнес-алерты (тикет + уведомление продакту):**
   - Количество заказов, «зависших» в статусе > N > 30 минут.
   - Полный цикл заказа > 3 недель.
   - Количество просроченных заказов > 10.

### 8.4. Настроить процессы

1. **On-call rotation** среди инженеров. Дежурный отвечает на критические алерты.
2. **Runbook** для каждого алерта: что делать, кого звать, как чинить.
3. **Postmortem** после каждого инцидента: что случилось, почему, как избежать.
4. **Регулярный review метрик** (раз в неделю) — продакт, тимлид, DevOps.
5. **Нагрузочное тестирование** перед каждым крупным релизом с использованием метрик.

### 8.5. Порядок внедрения

| Этап | Срок | Что делаем |
|---|---|---|
| 1 | 1–2 недели | Развернуть Prometheus + Grafana + Alertmanager, node_exporter, postgres_exporter, rabbitmq_exporter. |
| 2 | 2–4 недели | Подключить метрики к Shop API, CRM API, MES API. Настроить базовые дашборды. |
| 3 | 2–4 недели | Настроить критические алерты (DLX, HTTP 500, latency, CPU/Memory). |
| 4 | 1–2 месяца | Добавить кастомные бизнес-метрики (заказы, статусы, время расчёта). |
| 5 | 2–3 месяца | Настроить логирование и трассировку. Внедрить on-call и runbook. |
| 6 | 3–6 месяцев | Регулярный review метрик, нагрузочное тестирование, оптимизация. |

## 9. Показатели насыщенности

Насыщенность (saturation) — это степень, в которой ресурс исчерпан и не может обрабатывать новые запросы. Это ключевой показатель для USE-подхода.

### 9.1. Выбранные показатели насыщенности

| Компонент | Показатель | Порог | Почему такой порог |
|---|---|---|---|
| **EC2 (Shop API, CRM API, MES API)** | CPU % | **70%** — warning, **85%** — critical | При 70% начинается деградация latency из-за конкуренции за CPU. При 85% система близка к отказу. У компании **единственный инстанс** — нет запаса. |
| **EC2 (Shop API, CRM API, MES API)** | Memory Utilisation | **75%** — warning, **90%** — critical | При 75% начинается swap, что резко замедляет работу. При 90% — риск OOM. |
| **PostgreSQL (Shop DB, MES DB)** | Memory Utilisation | **75%** — warning, **90%** — critical | PostgreSQL активно использует память для кэша. При нехватке — уходит в диск, резко падает производительность. |
| **PostgreSQL (Shop DB, MES DB)** | Number of connections | **70%** — warning, **85%** — critical | Каждое соединение — это память и CPU. При приближении к лимиту новые соединения отклоняются, приложение падает. |
| **PostgreSQL (Shop DB, MES DB)** | Size of DB | **70%** — warning, **85%** — critical | При заполнении диска БД перестаёт писать. Нужен запас на рост (+100 заказов/мес). |
| **RabbitMQ** | Number of message in flight | **1000** — warning, **5000** — critical | Если in-flight растёт, потребители не справляются. Порог зависит от среднего времени обработки. |
| **RabbitMQ** | Number of dead-letter-exchange letters | **0** — warning, **> 0** — critical | Любое сообщение в DLX — это потерянный заказ. Недопустимо. |
| **S3** | Size of S3 storage | **70%** — warning, **85%** — critical | 3D-файлы растут линейно. Нужен запас на рост. |
| **API (все)** | Response time p95 | **2s** — warning, **5s** — critical | Пользователи ожидают быстрого ответа. 5 секунд — это уже неприемлемо. |
| **API (все)** | HTTP 500 rate | **0.5%** — warning, **1%** — critical | Даже 1% ошибок — это сотни потерянных заказов в день. |

### 9.2. Что должно происходить при превышении

#### Warning

1. **Автоматически создать тикет** в трекере (например Jira) с описанием: метрика, текущее значение, порог, компонент.
2. **Отправить уведомление в мессенджер** канал команды.
3. **Записать событие в лог** для последующего анализа.
4. **Дежурный инженер** проверяет в течение рабочего дня.

#### Critical

1. **Автоматически создать тикет** с высоким приоритетом.
2. **Отправить уведомление в мессенджер** + **звонок дежурному** (например Twilio).
3. **Запустить автоматическое масштабирование** добавить инстанс, увеличить ресурсы.
4. **Дежурный инженер** реагирует немедленно (в течение 15 минут).
5. **Если проблема не решается за 30 минут** — эскалация на тимлида и продакта.
6. **Если затронуты заказы** — уведомить продавцов и операторов через CRM/MES.
7. **После инцидента** — postmortem в течение 48 часов.

#### Специфические действия

| Метрика | При превышении |
|---|---|
| **DLX letters > 0** | Немедленно остановить потребителей, проверить сообщения в DLX, переобработать, починить баг. |
| **HTTP 500 rate > 1%** | Проверить логи, откатить последний релиз, если причина в нём. |
| **CPU > 85%** | Добавить инстанс (если есть автоскейлинг), либо оптимизировать код, либо увеличить ресурсы. |
| **Memory > 90%** | Перезапустить приложение (временно), увеличить память, найти утечку. |
| **Number of connections > 85%** | Увеличить лимит, добавить пул соединений, оптимизировать запросы. |
| **Size of DB > 85%** | Увеличить диск, настроить архивацию старых данных, добавить read-replica. |
| **Response time p95 > 5s** | Профилировать запросы, оптимизировать, добавить кэш. |
| **In-flight > 5000** | Добавить消费者 (consumers), увеличить prefetch, оптимизировать обработку. |

### 9.3. Почему именно такие пороги

- **Пороги выбраны с запасом**, потому что у компании сейчас **единственный инстанс** каждого приложения и БД. Нет резерва, поэтому нужно реагировать раньше.
- **70/85% для CPU/Memory** — это стандартные пороги для production-систем. При 70% начинается деградация, при 85% — риск отказа.
- **0 для DLX** — потому что любое потерянное сообщение = потерянный заказ = потерянный клиент.
- **1% для HTTP 500** — потому что при 100 заказах в день это 1 потерянный заказ ежедневно. При росте нагрузки это станет критично.
- **2s/5s для latency** — потому что пользователи ожидают быстрого ответа. 5 секунд — это уже раздражает, 10 секунд — уход.
- **Пороги для БД** — потому что БД — единственный инстанс, и её падение останавливает всё.

### 9.4. Автоматизация реакции

1. **Автоматическое масштабирование** (Yandex Cloud Autoscaling):
   - При CPU > 70% > 5 минут — добавить инстанс.
   - При CPU < 30% > 15 минут — удалить инстанс.
2. **Автоматический откат** при HTTP 500 rate > 5% после релиза.
3. **Автоматическая переобработка DLX** при появлении сообщений (с уведомлением).
4. **Автоматическое создание тикетов** через API трекера.
5. **Автоматический звонок дежурному** через Twilio при critical-алертах.

## 10. Выводы

1. **Мониторинг — это необходимость.** Без него компания не может понять, почему теряются заказы, и не может доказать, что улучшения работают.

2. **Разные подходы для разных частей системы:** RED для API, USE для инфраструктуры, «Четыре золотых сигнала» для RabbitMQ и бизнес-процессов.

3. **Начинать нужно с критических точек:** RabbitMQ (DLX, in-flight), ошибки API (HTTP 500), время ответа API. Это остановит потери и даст данные для дальнейших решений.

4. **Мониторинг должен быть сквозным:** от загрузки 3D-файла до закрытия заказа. Только так можно увидеть полную картину.

5. **Показатели насыщенности с порогами 70/85%** позволяют реагировать до того, как система упадёт. Автоматизация реакции (тикеты, звонки, масштабирование) снижает время реакции до минут.

6. **Бизнесу нужно показать экономический эффект:** мониторинг позволяет сохранить контракты, снизить отток клиентов и увеличить выручку. Это не затраты, а инвестиция.
